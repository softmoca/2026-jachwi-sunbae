# 프론트엔드 렌더링 성능 리포트

로딩이 끝난 뒤 사용자가 조작할 때(지도 드래그와 확대 축소, 동네 고르기, 바텀시트, 탭) 화면이 얼마나 매끄러운지를 재고 고친 기록이다. 성능 베이스캠프 미션의 렌더링 성능 개선(메인 스레드, 60fps, reflow와 repaint, 최소한의 변경)을 자취선배에 적용했다. 로딩 성능은 [로딩 성능 리포트](performance-report.md)에 있다. 이슈는 #542, #543, #556이다.

- 측정일: 2026-11-03 ~ 2026-11-04
- 처음 기준: develop `baa70c3d`(측정과 원인 찾기), `c3e931c5`(전후 비교)
- 원본(트레이스, React 커밋 기록, 스크린샷, 녹화)은 저장소 밖 `~/Documents/jachwi-perf/perf-rendering/`에 두고, 측정 폴더마다 README에 조건과 숫자를 적었다.

## 1. 측정 환경

| 항목     | 값                                                                                             |
| -------- | ---------------------------------------------------------------------------------------------- |
| 빌드     | 로컬 운영 빌드(`/api`만 dev API로 넘기는 정적 서버). 함수와 컴포넌트 이름은 개발 빌드로 확인   |
| API      | dev API. 운영 API와 운영 사이트로 재지 않는다. PostHog 토큰은 비운다                           |
| 브라우저 | Playwright Chromium 헤드리스, 실행마다 새 프로필, 확장 없음, GPU ANGLE Metal(Apple M1)         |
| 화면     | 휴대폰 390x844 DPR 3. 시트 폭은 768px, 1023px도 본다                                           |
| CPU      | 녹화 구간에만 4x slowdown                                                                      |
| 회수     | 시나리오마다 3회. 전후 비교는 같은 시간대에 개선 전 빌드와 번갈아 잰다(before 1, after 1, ...) |

프레임은 DevTools Frames 트랙과 같은 `PipelineReporter` 상태(드롭, 부분 표시)로 센다. INP 후보는 녹화 안 인터랙션 가운데 가장 긴 것이다. React 리렌더는 React DevTools Profiler와 같은 판정(`PerformedWork`, 바뀐 서브트리만)으로 커밋마다 렌더된 컴포넌트와 이유를 기록했다. 헤드리스라 확장 패널 대신 같은 훅을 넣었다.

측정하다 바로잡은 것이 둘 있다. 트레이스 분류에 `invalidationTracking`을 켜면 DOM을 바꾸는 비용이 크게 부풀어(탭 전환 INP 495ms가 끄니 131ms) 끄고 다시 쟀다. 녹화 중에 Playwright로 요소를 찾으면 접근성 이름 계산이 트레이스에 섞여, 요소 위치는 녹화 전에 구해 두었다.

- 같은 드래그가 빈 지도에서는 드롭이 없으므로 결과 지도의 버벅임은 경계 다각형에서 나온다. 경기 행정동 601개를 따로 띄운 실험에서 `naver.maps.Data` 레이어로 바꿔도 비용이 거의 같았다(Data 레이어도 기능마다 소스를 둔다). 색별로 합치는 방법은 GL Polygon이 외곽 링 여러 개를 그리지 못해 막혀 있다.
- develop(`c3e931c5`)에서는 지도가 멈출 때마다(idle) 동네 찾기 화면 전체(컴포넌트 약 35개)가 다시 렌더됐다. 드래그를 멈춘 뒤에도 입력 없이 지도를 10초 넘게 계속 다시 그린 구간이 있었다.
- 매물 등록에서 단 거리 메모가 결과 지도에 보이는 것과 "이전 탭 마커가 남는다"는 제보는 지도 인스턴스에 올라간 마커를 상태마다 세어 가렸다. 모든 상태에서 지도에 붙은 수, DOM 수, 요청된 수가 같았고, 메모는 동네를 고르지 않은 상태에서 메모 레이어로만 들어왔다.

## 4. 개선과 결과

전후는 develop `c3e931c5`와 이 작업 빌드를 같은 시간대에 번갈아 3회씩 쟀다(CPU 4x). 지도 조작은 두 번(1회차, 2회차) 쟀다.

- 컴포넌트 렌더 수, 탭 전환, 시트 끌기는 두 회차 모두 같은 방향으로 줄었다.
- 지도 드래그, 확대 축소의 프레임과 긴 작업은 1회차에서 개선 전만 크게 나빴는데(드래그 뒤 입력 없이 지도를 10초 넘게 계속 다시 그림) 2회차에서는 재현되지 않았다. 2회차 차이는 회차 사이 흔들림 안팎이라 개선되었다고 보지 않는다. 리렌더가 지도를 다시 그리게 만드는지, 그 경로가 무엇인지도 확인하지 못했다.
- 핀치 중 프레임은 줄었다고 볼 수 없다. 지도 비용의 본체(경계 소스마다 매 프레임 타일 계산)는 이번 변경으로 줄지 않는다.
- 동네 고르기와 분석 → 결과는 GL 경계 등록과 확대 애니메이션이 대부분이라 회차 사이 흔들림이 차이보다 크다.

| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
