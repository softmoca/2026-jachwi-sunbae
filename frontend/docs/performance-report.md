# 프론트엔드 로딩 성능 리포트

어느 화면의 성능을 계속 지킬지, 무엇으로 재고 어디까지를 허용할지, 지금 어디가 넘치고 무엇을 고쳤는지를 적는다. 성능 베이스캠프 미션(성능 리포트, 로딩 성능 개선)을 자취선배에 적용한 결과다. 이슈는 #534다.

- 측정일: 2026-11-03 ~ 2026-11-04
- 처음 기준: develop `baa70c3d`
- 렌더링(런타임 프레임, 리렌더, INP)은 별도 작업에서 다룬다. 이 문서의 해당 칸은 "렌더링 작업에서 측정"으로 둔다.

## 1. 관리할 화면

| 화면            | 주소                         | 왜 지키는가                                                                                                                                   |
| --------------- | ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 첫 진입 홈      | `/`                          | 회원 화면의 입구다. 앱 웹뷰와 웹 모두 여기서 시작하고 자동 로그인과 함께 그린다. 운영 모바일 LCP p75가 2,754ms로 홈만 "개선 필요" 구간이었다. |
| 동네 찾기 결과  | `/neighborhoods`, `/explore` | 광고 유입의 목적지이자 새 핵심 기능이다. 통근 API, 시도별 행정동 경계, 지도 SDK를 모두 받아야 결과가 보여 가장 무겁다.                        |
| 본 방 기록 지도 | `/properties?view=map`       | 집을 보며 기록하는 본래 기능이다. 매물 마커가 보여야 쓸 수 있다.                                                                              |
| 광고 랜딩       | `/landing`                   | 신규 사용자의 첫인상이다. 첫 화면에 소개 영상이 있다.                                                                                         |

### 모바일을 기준으로 한다

- 운영 PostHog 최근 30일(내부 계정 제외)의 방문자는 데스크톱 71명, 모바일 69명으로 비슷하지만 페이지뷰는 모바일 3,362회, 데스크톱 1,017회로 모바일이 3.3배다.
- 집을 보러 다니면서 휴대폰으로 기록하는 서비스이고, React Native 앱(`mobile/`)도 같은 웹을 웹뷰로 연다.
- 같은 화면을 데스크톱 조건으로 재면 동네 결과(70점)를 빼고 Lighthouse 95점 이상이라 문제는 모바일 조건에서 드러난다. 데스크톱은 회귀를 막는 보조 기준으로만 잰다.

## 2. 지표와 성능 예산

### 기준 환경

| 항목              | 모바일(기준)                                                                                                                                         | 데스크톱(보조)                       |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| Lighthouse 13.6.0 | 기본 설정(Moto G Power 412x823, simulate 150ms RTT, 1.6Mbps, CPU 4x)                                                                                 | desktop 프리셋(40ms, 10Mbps, CPU 1x) |
| 사용자 지표 실측  | Playwright와 CDP, 412x823 DPR 1.75, DevTools Slow 4G(562.5ms, 1.47Mbps/675kbps), CPU 4x                                                              | 1350x940, 40ms, 10Mbps, CPU 1x       |
| 공통              | 로컬 운영 빌드(dev API를 프록시), dev CloudFront와 같은 압축과 캐시 헤더, 실행마다 새 프로필(빈 캐시, 확장 없음), PostHog 요청 차단, 3회 이상 중앙값 | 같음                                 |

- 운영 API와 운영 사이트로는 재지 않는다(분석 데이터 오염). 같은 dev 익명 회원과 측정용 매물 5개를 쓴다.
- 기계 상태에 따라 같은 빌드도 Lighthouse 점수가 10점 넘게 흔들린다. 전후 비교는 같은 시간대에 기준과 개선 후를 번갈아 잰 값만 쓴다.

### 사용자 지표

지도 화면의 LCP는 지도가 아니라 지도 위 안내 글자를 잡아서(동네 찾기 LCP 0.6초) 지도가 보였는지를 대신하지 못한다. 그래서 앱 코드를 바꾸지 않고 측정 스크립트에서 다음 시각을 잡는다.

| 지표          | 정의                                                                  |

| 지도 SDK 준비 | 네이버 SDK 완료 콜백(`jachwiNaverSdkReady`)이 불린 시각               |

## 3. 처음 측정과 원인

### 이미 잘 되어 있던 것

- dev CloudFront가 JS를 brotli와 gzip으로 내려준다(`main` 344KiB → brotli 105KB). HTTP/2다.
- 해시 파일은 `public,max-age=31536000,immutable`, `index.html`과 경계 manifest는 `no-cache,max-age=0,must-revalidate`다.
- 모든 화면이 `lazy()`로 나뉘어 있고 웹 폰트를 받지 않는다.

### 예산을 넘은 곳

| 화면           | 원인 (HAR 워터폴, 번들 분석, Coverage)                                                                                                                          |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 동네 결과      | 경기 경계 파일이 gzip 1,089KB이고 좌표가 소수점 15자리였다. 순위 마커는 결과 지역의 경계를 모두 받은 뒤 나온다. 통근 API 응답 470KB가 압축 없이 온다.           |
| 기록 지도      | 매물 목록이 올 때까지 지도를 붙이지 않아 네이버 SDK가 4.9초에야 출발했고, `maps.js`가 끝난 뒤에야 `maps-gl.js`(269KB)를 받는 직렬 구간이 있었다.                |
| 모든 지도 화면 | 마커 HTML을 `renderToStaticMarkup`으로 만들려고 `react-dom/server`를 불러, 쓰지 않는 스트리밍 렌더러까지 서버 렌더러 두 개(압축 전 188KB, 81% 미사용)를 받았다. |
| 랜딩           | 첫 화면 소개 영상 4.5MB와 화면 캡처 JPG(장당 최대 454KB)를 받았다.                                                                                              |
| 동네 결과 CLS  | 결과 경계 전체가 보이도록 지도가 4단계 줌아웃하는 동안 네이버 래스터 타일(256px `<img>`)이 크기와 위치 속성으로 움직였다. 글자나 목록이 밀린 기록은 없다.       |

## 5. 하지 않은 것과 다음 후보

| 후보                             | 판단                                                                                                                                                                             |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PostHog SDK를 `load` 뒤로 미루기 | 재 보니 SPA의 `load`가 첫 화면 청크 직후(약 1.9초)에 와 SDK 출발이 거의 같았다. 더 늦추면 빨리 떠나는 방문의 이벤트를 잃을 위험이 커지는데 얻는 대역폭은 약 0.4초라 넣지 않았다. |
| 순위 마커를 경계보다 먼저 보이기 | 동네 결과 표시를 가장 크게 당길 수 있다. 화면 동작이 바뀌어 따로 판단한다.                                                                                                       |
| 마커를 React portal로 그리기     | 서버 렌더러를 통째로 뺄 수 있다. `createRoot`로는 effect 안에서 `flushSync`가 거절돼 막혔고, 마커 수명 관리를 다시 짜야 해 렌더링 작업에서 다룬다.                               |
| 결과 화면 CLS                    | 처음 결과는 애니메이션 없이 맞추거나 GL 캔버스로 타일을 그리는 안이 있다. 렌더링 작업으로 넘긴다.                                                                                |
| 통근 API 응답 압축               | 백엔드 `server.compression` 설정이 없다. 백엔드에 전달한다.                                                                                                                      |
| 홈 LCP                           | LCP 요소(`card-neighborhood.webp`, 10KB)보다 JS가 화면을 그리기까지의 지연이 크다. `main`의 54%가 홈에서 쓰이지 않는다. 화면 동작을 바꾸지 않는 분리 방법을 따로 찾는다.         |
