# CI 실행 범위와 시간 측정

## 변경 범위

이번 변경은 GitHub Backend CI의 불필요한 실행을 줄이고 의존성 캐시 재사용을 개선한다. Frontend CI와 프론트엔드 소스·테스트·설정, AWS 파이프라인은 변경하지 않는다.

워크플로 수정은 PR을 통해 develop에 반영한다. 개선 후 시간은 원격 CI에서 별도로 측정하며, 결과 확인 전에는 단축률을 확정하지 않는다.

Backend CI는 `backend/docs/**`와 `backend` 바로 아래 Markdown만 바뀌면 Java·Gradle 준비와 빌드를 생략한다. 필수 상태 검사인 `Build`는 계속 보고하며 Markdown CI는 기존과 같이 문서를 검사한다. 소스와 리소스 안의 Markdown, 테스트, 마이그레이션, 배포 스크립트, 백엔드 CI와 Gradle 초기화 스크립트 변경은 빌드를 실행한다.

경로를 옮긴 경우 원래 경로의 삭제도 검사하도록 `git diff --no-renames`를 사용한다. 문서 경로로 옮긴 소스 때문에 빌드가 잘못 생략되는 것을 막는다. 수동 실행은 변경 경로와 관계없이 빌드한다.

기존 `clean build --no-daemon`에 `--build-cache`와 CI 전용 초기화 스크립트를 추가한다. Java 테스트 범위는 유지하고 Test 작업의 결과 캐시와 up-to-date 생략을 끈다. 컴파일 캐시 적중 여부와 관계없이 테스트를 실행한다.

## 의존성 캐시와 작업 결과 캐시

두 종류의 캐시를 분리한다. 큰 의존성 캐시를 소스 커밋마다 복제하지 않고, 작은 작업 결과 캐시만 커밋별로 갱신한다.

| 종류      | 경로                                             | 키와 복원 방식                                                                                          |
| --------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| 의존성    | Gradle User Home의 절대 경로 `caches`, `wrapper` | 실행 환경과 백엔드 Gradle 설정으로 키를 만들고, 이전 백엔드 캐시 또는 기존 `setup-java-...` 캐시를 복원 |
| 작업 결과 | `runner.temp/backend-gradle-task-cache`          | 실행 환경·Gradle 설정·CI 초기화 스크립트·커밋 SHA로 저장하고, 이전 커밋의 캐시도 복원                   |

의존성 캐시는 최초 PR부터 기본 브랜치의 기존 캐시를 재사용한다. 기존 basic provider가 저장한 `/home/runner/.gradle/caches`와 `/home/runner/.gradle/wrapper`의 순서와 절대 경로를 맞춘다. GitHub 캐시는 경로와 압축 방식도 버전 해시에 넣으므로 키 접두어만 맞추는 것으로는 기존 캐시를 읽을 수 없다.

`setup-gradle`을 먼저 실행해 `GRADLE_USER_HOME`을 설정하고 `cache-provider: external`로 중복 캐시 관리를 끈다. 그 뒤 두 캐시를 복원한다. 설정이 같은 작업 결과 캐시를 우선 복원하고, 없으면 같은 실행 환경의 이전 캐시를 복원해 Gradle이 작업별 입력을 다시 판단한다. 캐시가 없어도 Gradle은 필요한 의존성을 다운로드하고 정상 빌드를 수행한다.

성공한 동일 저장소 PR과 push·수동 실행은 새 캐시를 저장한다. fork PR은 읽기만 한다. PR 캐시는 해당 PR의 후속 커밋·재실행에 사용되며 다른 PR이 읽는 공유 캐시와 구분된다. 기본 브랜치에서 저장한 캐시는 새 PR에서도 복원할 수 있다. 기존 키가 정확히 적중하면 같은 키를 다시 저장하지 않는다.

## 테스트 실행과 단계별 계측

[CI 초기화 스크립트](../../.github/gradle/backend-ci.init.gradle)는 CI 실행에만 작업 결과 캐시 경로와 테스트 정책을 적용한다. 애플리케이션의 Gradle 설정과 로컬 기본 빌드·AWS 배포 명령은 바꾸지 않는다.

`--build-cache`를 사용하면 같은 입력의 Java 컴파일 등을 `FROM-CACHE`로 복원할 수 있다. 소스·클래스패스 등 입력이 바뀌면 Gradle이 다시 실행한다. `clean`은 유지하며 프로젝트의 이전 빌드 디렉터리를 그대로 복원하지 않는다.

Test 작업은 `outputs.cacheIf { false }`와 `outputs.upToDateWhen { false }`로 매 실행 수행한다. 각 작업은 `CI_TASK :작업명 elapsed_ms=... outcome=...`를 출력해 컴파일 재사용과 실제 테스트 실행 시간을 구분한다.

캐시만 수정한 원격 실행에서도 Test 작업이 약 3분 39초를 차지해 CI에서 테스트 JVM을 최대 2개로 제한해 병렬 실행한다. JUnit의 같은 JVM 내부 스레드 병렬화는 켜지 않는다. `CI_TEST_CONFIG`와 `CI_TEST_SUMMARY`로 실제 fork 수, 테스트 건수, 실패·생략 건수를 확인한다. 기존 태그 제외 정책은 유지하고 테스트 파일을 수정하거나 제외하지 않는다.

## 개선 전 기준선

2026-11-02에 최근 100개 GitHub Actions 실행 중 FE·BE·Markdown·Storybook 97개를 조회했다. 취소 2개를 제외하고 실제 검사 실행과 변경이 없어 생략한 실행을 구분했다.

| 구분        | 실제 검사 표본 | 전체 완료 시간 중앙값 | 범위              |
| ----------- | -------------- | --------------------- | ----------------- |
| Backend CI  | 4회            | 4분 57초              | 3분 56초~6분 30초 |
| Frontend CI | 26회           | 2분 47초              | 1분 44초~4분 8초  |
| Markdown CI | 30회           | 18초                  | 16초~1분 3초      |
| Storybook   | 8회            | 약 1분 21초           | 1분~2분 26초      |

전체 완료 시간은 워크플로 생성부터 마지막 실행 잡의 완료까지이며 시작 대기와 잡 사이 대기를 포함한다. 서로 병렬로 실행되는 워크플로 시간을 합산해 사용자 대기 시간으로 해석하지 않는다. 관련 변경이 없는 BE 실행의 중앙값은 이미 14초였으므로 이를 새 개선 효과로 계산하지 않는다.

BE 표본은 캐시 적중 1회와 미적중 3회로 적다. 서로 다른 커밋의 관측값이므로 이 차이 전체를 캐시의 효과로 단정하지 않는다. 원본은 저장소에 사용자별 경로를 넣지 않고 별도 측정 자료로 보관한다.

## AWS 분리

GitHub CI는 코드 검증, AWS 파이프라인은 빌드·배포를 담당한다. 이번 변경은 AWS 콘솔 설정이나 배포 명령을 바꾸지 않으므로 GitHub 검사를 생략해도 기존 AWS 배포는 시작될 수 있다.

AWS 최적화는 별도 작업으로 진행한다. 롤백 상태를 구분하지 않고 실행 중인 SHA만 비교하면 다음 FE 변경에서 의도적으로 롤백한 BE 코드가 다시 배포될 수 있어 기존 초안을 적용하지 않는다.

## 전후 비교 방법

1. 문서 전용 변경, BE 코드 변경, 빌드 설정 변경, 수동 실행을 각각 비교한다. 워크플로 자체가 바뀐 PR은 반드시 전체 빌드하므로 문서 전용 생략 사례로 계산하지 않는다.
2. 각 실행의 커밋·이벤트·런너·캐시 상태·잡 및 단계별 시작과 완료 시각을 기록한다. 전체 완료 시간과 Build 단계 시간을 구분한다.
3. 불필요한 실행 횟수와 총 작업 시간 감소, 필요한 빌드의 실행 시간 감소를 나눈다.
4. 동일 조건의 변경 전후 실행을 반복해서 중앙값과 범위를 비교하고 표본 수를 함께 표시한다.
5. 기존 의존성 캐시 복원, 작업 결과 캐시 최초 미적중, 같은 커밋 재실행의 정확한 적중, 후속 커밋의 접두어 복원을 구분한다. 실제 복원된 키와 테스트 실행 여부도 기록한다.
6. 같은 커밋을 반복 실행해 측정하고 후속 커밋도 검사한다. 로컬 검증은 원격 캐시 복원·저장을 대체하지 않으며, 최초 실행 한 번으로 개선 효과를 단정하지 않는다.
