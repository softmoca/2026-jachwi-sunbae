# 편의점 행사상품 기능 명세

- 상태: 확정 / 제품 버전: Unreleased / 수정일: 2026-10-29

## 1. 목적과 범위

자취생은 편의점을 방문하기 전에 해당 브랜드의 1+1, 2+1 등 행사상품을 한곳에서 확인한다.

이마트24와 세븐일레븐 공식 홈페이지의 행사상품을 하루 한 번 수집·저장하고, 저장된 전체 목록을 조회하는 백엔드 기능을 다룬다. 상품 목록·카드 UI, 검색·정렬·필터 UX, 지도의 주변 편의점 연동, CU·GS25 등 다른 브랜드 수집, 상품명 기반 카테고리 분류, 증정행사 상세 조건과 상품 추천은 범위에 포함하지 않는다.

## 2. 요구사항

- `REQ-PROMOTION-001`: 서버는 이마트24와 세븐일레븐 공식 행사상품 페이지에서 상품명, 판매가격, 이미지 URL, 상품 카테고리, 행사 유형을 수집한다.
- `REQ-PROMOTION-002`: 상품 카테고리는 간편식사·과자·음료·생활용품·미분류(`UNKNOWN`), 행사 유형은 1+1·2+1·3+1·세일·골라담기로 구분한다.
- `REQ-PROMOTION-003`: 서버는 매일 한 번 전체 목록을 수집해 브랜드의 기존 목록을 새 목록으로 교체한다.
- `REQ-PROMOTION-004`: 사용자는 브랜드의 저장된 행사상품 전체와 마지막 정상 수집 시각을 조회한다.
- `REQ-PROMOTION-005`: 사용자는 행사상품 정보를 가져온 브랜드 공식 페이지(출처)를 확인한다.

## 3. 정책

### 3.1. 수집과 저장

- `POL-PROMOTION-001`: KST 매일 04:00에 수집한다. 실패해도 즉시 재시도하지 않고 다음 날 다시 수집한다.
- `POL-PROMOTION-013`: 서버 기동 5분 뒤 목록이 없는 브랜드만 한 번 수집한다. 이미 목록이 있으면 재배포해도 수집하지 않는다.
- `POL-PROMOTION-002`: 이마트24는 네 카테고리의 모든 페이지를 수집하고, 응답의 전체 상품 수와 실제 수집 건수가 같아야 성공이다. 요청 실패, 접근 제한, 응답 형식 변경이 하나라도 있으면 수집 전체가 실패한다.
- `POL-PROMOTION-003`: 브랜드·상품명·가격·이미지 URL·카테고리·행사 유형이 모두 같은 항목만 하나로 합친다. 상품명이 같아도 다른 값이 하나라도 다르면 별개의 행사로 유지한다.
- `POL-PROMOTION-004`: 수집에 성공했을 때만 해당 브랜드의 기존 목록을 삭제하고 새 목록을 저장하며, 두 작업은 함께 반영되거나 함께 취소된다. 수집 또는 저장에 실패하면 해당 브랜드의 마지막 정상 목록과 수집 시각을 유지한다.
- `POL-PROMOTION-005`: 외부 요청 사이에 최소 1초 간격을 둔다.
- `POL-PROMOTION-014`: 브랜드는 독립적으로 수집·저장한다. 한 브랜드의 수집이나 저장이 실패해도 다른 브랜드의 수집과 기존 목록에 영향을 주지 않는다.

### 3.2. 조회

- `POL-PROMOTION-006`: 조회는 저장된 데이터만 사용하며 외부 홈페이지를 호출하지 않는다.
- `POL-PROMOTION-007`: 페이지네이션, 검색, 서버 측 필터 없이 브랜드의 전체 목록을 저장 순서로 반환한다. 카테고리·행사 유형 필터는 클라이언트에서 처리한다.
- `POL-PROMOTION-008`: 저장된 상품이 없으면 오류가 아니라 빈 목록과 `collectedAt=null`을 반환한다.
- `POL-PROMOTION-009`: 수집 시각은 `+09:00` 오프셋을 포함한 KST 시각이다.

### 3.3. 데이터 제약

- `POL-PROMOTION-010`: 행사상품은 브랜드 공통 행사 정보다. 특정 매장의 판매가격, 재고나 행사 적용 여부를 보장하지 않는다.
- `POL-PROMOTION-011`: 데이터 출처는 각 브랜드 공식 홈페이지이며, 브랜드에 문의해 안내받은 이용 범위(상품명·판매가격·이미지·카테고리·행사 유형)만 사용한다. 이미지는 내려받지 않고 공식 이미지 URL을 그대로 제공한다. 조회 응답의 `sourceUrl`로 공식 행사상품 페이지를 함께 반환한다.
- `POL-PROMOTION-012`: 목록은 최대 하루 전 상태일 수 있다. 사용자는 `collectedAt`으로 갱신 시각을 확인한다.

### 3.4. 세븐일레븐

- `POL-PROMOTION-015`: 세븐일레븐 고객센터에서 "공식 홈페이지 출처를 밝히고, 1일 1회 연동 시 사용 가능"하다는 답변을 받았다. 이를 지키기 위해 다음과 같이 운영한다.
  - 자동 수집은 기본으로 꺼져 있으며 `promotion.collection.seven-eleven.enabled=true`인 환경에서만 수집한다. 행사상품 스케줄러(`promotion.collection.enabled`)도 함께 켜져 있어야 한다.
  - 켠 뒤 기동 5분 뒤에 최초 적재하고 이후 04:00에 수집한다. 목록이 있으면 재시작·재배포해도 수집하지 않는다.
  - 00:00~04:00 사이에 최초 적재하면 같은 날 04:00 수집까지 2회가 된다. 최초 적재가 실패한 날 다시 배포하면 그날 다시 요청한다. 최초 적재 배포는 04:00 이후에 하고, 실패하면 다음 04:00을 기다린다.
  - Dev·Prod는 각자 04:00에 수집하므로 세븐일레븐 수집은 **한 환경에서만** 켠다.
- `POL-PROMOTION-016`: 1+1·2+1·할인행사 탭을 수집해 각각 `ONE_PLUS_ONE`·`TWO_PLUS_ONE`·`SALE`로 저장한다. 증정행사 탭은 구매·증정 조건을 확인하지 못해 수집하지 않는다. 공식 상품 카테고리를 확인할 수 없어 모든 상품을 `UNKNOWN`으로 저장하며 상품명으로 추정하지 않는다.
- `POL-PROMOTION-017`: 탭마다 첫 화면의 전체 상품 수를 채울 때까지 더보기를 요청한다. 다음은 부분 수집으로 인정해 저장한다.
  - 더보기 응답이 기대보다 적게 오면 그 탭의 요청을 멈춘다.
  - 그때까지 확보한 상품이 전체 수의 98% 이상이면 부분 수집으로 인정한다. 누락 규모는 경고 로그로 남긴다.
  - 98% 미만, 빈 더보기 응답, 기대보다 많은 응답, 필수 필드·HTML 구조 오류, HTTP 오류·시간 초과, 최대 250페이지 초과는 수집 실패로 처리한다.

## 5. 세븐일레븐 검증 기록

`test-con` 브랜치에서 2026-10-29에 실제 데이터를 한 번 수집했다.

| 행사 유형 | 공식 표시 건수 | 확보 건수 | 비고                                        |
| --------- | -------------: | --------: | ------------------------------------------- |
| 1+1       |            919 |       919 | 92페이지의 마지막 6건까지 수집              |
| 2+1       |            926 |       926 | 93페이지의 마지막 3건까지 수집              |
| 증정      |              0 |         0 | 수집 대상에서 제외(`POL-PROMOTION-016`)     |
| 할인      |            484 |       480 | 48페이지가 기대한 10건 대신 7건 반환(99.2%) |
| 합계      |          2,329 |     2,325 |                                             |

- 확보한 HTML을 재요청 없이 재생해 확인한 결과, 모든 필드가 같은 중복 1건을 제외한 2,324건이 Testcontainers MySQL에 저장되고 기존 조회 API로 2,324건이 반환됐다. 저장·조회 검증은 DB 기동을 포함해 11.98초였다.
- 실제 수집은 요청 간격을 포함해 약 9분이 걸렸다. 2+1 80페이지는 21.7초가 걸려, 응답 읽기 제한을 30초로 두었다.
- 할인 48페이지의 짧은 응답이 실제 전체 수의 변화인지, 뒤 페이지에 상품이 더 있는지는 확인하지 못했다.
- 위 결과는 일회용 DB에서의 검증이며 Dev·Prod 데이터 적재 결과가 아니다.
- 정식 구현의 Parser·Fetcher·저장·조회 테스트는 실제 HTML을 축약한 fixture로 검증하며 세븐일레븐 홈페이지에 요청하지 않는다. 할인 48페이지의 실제 응답으로 부분 수집 인정(480/484건)을 회귀 테스트한다.

## 6. 세븐일레븐 Dev 적용 전 확인 사항

1. 세븐일레븐 수집을 켤 환경을 하나로 정한다. Dev에서 검증할 경우 `application-dev.yml`에만 `promotion.collection.seven-eleven.enabled: true`를 추가하고 Prod는 끈 상태로 둔다.
2. 04:00 KST 이후에 배포해 기동 5분 뒤 최초 적재를 확인한다. 같은 날 별도로 세븐일레븐에 요청하거나 재배포하지 않는다.
3. 수집 결과를 로그로 확인한다.
   - 성공: `promotion-collection-end brand=SEVEN_ELEVEN success=true`의 `rawCount`·`duplicateCount`·`storedCount`
   - 부분 수집: `promotion-seven-eleven-partial-collection`의 `tab`·`totalCount`·`collectedCount`·`missingCount`
   - 실패: `promotion-seven-eleven-request-failed` 또는 `success=false`. 당일 재시도하지 않고 다음 04:00을 기다린다.
4. `GET /api/promotions?brand=SEVEN_ELEVEN`의 `count`, `collectedAt`, `sourceUrl`, `category=UNKNOWN`을 확인한다.
5. 기존 `brand=EMART24` 조회의 상품 수와 수집 시각이 바뀌지 않았는지 확인한다.

## 7. 미정사항

- 한 번에 전체 조회: 초기에는 2천여 개의 최신 행사 항목을 프론트에서 필터링하는 방향으로 검토한다. JSON 응답 크기·로드 시간·모바일 성능을 측정해 페이지네이션이나 서버 필터가 필요한지 판단한다. 상품 이미지는 한꺼번에 요청하지 않도록 지연 로딩을 검토한다.
